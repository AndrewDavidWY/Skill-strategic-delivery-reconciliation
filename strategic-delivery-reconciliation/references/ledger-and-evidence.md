# 台账与证据约定

## 最小数据结构

`portfolio.example.json` 是完全虚构的示例，不是公司制度或固定字段要求。可按团队既有系统映射。

- `objectives`：稳定 ID、目标、成功条件、决策来源及明确的 `required_dimensions`。
- `packages`：稳定 ID、目标 ID、交付描述、负责人、集成人、编辑范围、到期日、依赖、验收条件、完成声明。
- `dimensions`：每个包对三种维度明确适用性，不适用必须给原因。目标要求的维度必须由至少一个未取消交付包的条件覆盖。
- `criteria`：条件 ID、所属维度 `code` / `live` / `business`、可观察的验收描述。ID 在单个包内唯一；`expected_version` 和 `expected_environment` 约束证据范围，live 条件还需正数 `freshness_hours`。
- `dependencies`：上游 `package_id`、所需 `dimension` 和本包受影响的 `affects_dimension`。有依赖不代表必须等待整个上游业务周期结束。
- `evidence`：包、条件、结果 `passed` / `failed` / `pending`、来源、观察时间、对应版本和环境；可设 `expires_at`。
- `claim`：`complete`、`in_progress`、`blocked`、`not_started` 或 `cancelled`。声明与脚本推导状态分开，不能用脚本覆盖真实项目决策。

时间戳使用带时区的 ISO 8601；日期字段用于到期日，不与观察时刻混用。证据最新不等于更正确：脚本按观察时间选择最新记录，若时间相同且相互冲突，标记冲突。对历史回滚、替代版本和证据有效范围，需要执行者判断后更新台账。

## 证据层次

| 维度 | 可接受的证据例子 | 不能替代的证据 |
| --- | --- | --- |
| 代码/产物 | 确定提交上的检查、打开验证的文件、已完成的交付清单 | “已经写好”、本地测试旧版本 |
| 上线/运行 | 目标环境部署版本、实际 URL 与观察、真实集成结果 | PR 已合并、预览站运行、部署配置已添加 |
| 业务结果 | 明确验收、真实业务指标与观察窗口、流程实际采用 | 埋点安装、技术检查通过、计划中的客户确认 |

证据记录应包含“对哪个版本/范围做了什么检查、观察到什么、何时观察、谁确认、限制是什么”。不要为填字段杜撰截图、链接、客户批准或测试结果。

## 脚本结果边界

`reconcile_portfolio.py` 是离线一致性检查器：读取 JSON，向标准输出写 JSON，不修改外部系统。

- 每个维度的条件都为有效 `passed` 才显示 `passed`。
- 任何条件失败则该维度 `failed`；过期为 `stale`；缺失或未执行为 `pending`；同时间矛盾为 `conflict`；版本或环境不匹配为 `mismatch`。
- 无该维度的条件只有在明确声明不适用并说明原因后才是 `not_applicable`。`ready_dimensions` 按受影响维度传播依赖阻塞，不用上游无关的业务验收阻挡代码交接。
- `claim=complete` 但验收/依赖未满足时，输出矛盾并返回退出码 2。
- 结构无效、重复 JSON 键、循环依赖、未知引用或未来证据也返回 2；正常但未完成的计划仍可返回 0。拒绝重复键以免完成声明或证据字段被静默覆盖。

来源只是定位符，脚本不会联网核验，也不检查文本背后的法律、商业或权限约束。正式结项仍需读取最新来源。
